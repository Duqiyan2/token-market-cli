## What to build

已有连接的用户下一次主动 Connect 或 Reconnect 时，为旧规则连接范围创建一个
独立的新 Key，并按 Bound Workspace 应用新命名。新凭据安全保存并提交工具配置后，
后续 CLI 与桌面连接复用它；历史 Key 的名称、密钥和状态保持原样。

## Acceptance criteria

- [ ] 旧规则采用明确的持久化识别方式；每个范围首次迁移创建不同 ID 的新 Key，随后正常重连不再新增 Key。
- [ ] 平台协议和 CLI/桌面共享连接流程明确区分规则迁移、普通复用和凭据丢失恢复；迁移不误报本地凭据丢失，也不要求用户手动清除缓存。
- [ ] 旧凭据存在于缓存、连接记录、工具配置或平台绑定时，均不会绕过首次替换；平台尚无绑定但可以按指纹认领旧 Key 的情况同样覆盖。
- [ ] 个人空间迁移后得到仅工具名的 Key，企业空间得到带手机号或用户 ID 的 Key，格式与新范围一致。
- [ ] 历史 Key 不改名、不重置密钥、不删除、不停用，且不加入接入完成时会停用它的恢复链路。
- [ ] 保存新凭据、确认保存、加载 Model Catalogue、提交配置及确认接入完成沿用现有顺序，迁移采用状态和未完成签发状态持久化。
- [ ] 新 Key 接入完成后，CLI 与桌面共享复用；手机号或名称后来改变不触发再次迁移，普通凭据丢失仍遵循现有显式恢复规则。
- [ ] 登录、启动及后台查询不会自动替换现有工具配置；迁移仅由用户主动 Connect 或 Reconnect 触发。
- [ ] 现有账号、空间、设备、Tool、客户端身份和服务地址边界保留，停用、过期、权限及归属校验不被绕过；协议不兼容时保留原有凭据和配置并给出可理解的失败结果。
- [ ] 在既有客户端协议和平台服务测试中，从真实旧规则状态完成一次迁移，并断言一个历史 Key 与一个新规则 Key 共存、工具使用新 Key、再次重连不新增 Key。
