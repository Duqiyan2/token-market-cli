## What to build

迁移过程中遇到网络故障、保存失败或客户端退出的用户，可以通过重试或重启继续
同一次迁移。已经安全保存的新 Key 会被复用，尚未完成的签发会被恢复，原配置
在切换成功前保持可用，历史 Key 始终不因本次迁移被修改。

## Acceptance criteria

- [ ] 签发已提交但响应丢失时，重试或重启收敛到同一个新 Key 记录；不得创建第二个新规则 Key 或重置历史 Key。
- [ ] 新 Key 尚未安全保存时不确认保存、不发布引用它的工具配置；凭据存储被锁定、不可读或写入失败时保留原配置。
- [ ] 安全保存成功但确认响应丢失时，重试使用保存的新凭据继续，不误报凭据丢失、不重新签发。
- [ ] Model Catalogue 加载失败或配置提交失败后，重试继续使用已保存的新 Key，并保留原配置中的用户修改。
- [ ] 覆盖签发后、保存后、配置提交前后及接入完成确认丢失等中断点，重启后可以继续完成迁移。
- [ ] 普通网络、权限、模型及存储错误不会被解释为 Key 不存在，亦不会清空可用凭据或触发多余迁移。
- [ ] 每个故障场景均断言历史 Key 的名称、密钥和状态不变，最终配置使用唯一的新 Key，后续重连继续复用。
- [ ] 个人与企业空间均保留正确命名和范围隔离，CLI 与桌面可接续同设备的未完成迁移。
- [ ] 沿用现有本地 HTTP 故障夹具、临时目录和测试凭据存储，并补充平台恢复行为验证，以可观察结果检验恢复流程。
