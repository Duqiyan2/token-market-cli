# Client Key naming contract

`POST /api/client/keys/{inspect,issue,recover,confirm,applied}` retains its existing authentication, workspace permissions, device/tool scope, fingerprints and issuance request/generation semantics.

The optional integer request field `naming_version` advertises the client's understood naming rule: absent or `0` is the original protocol; `1` understands workspace-aware Token Market names. Other values are rejected before issuance. It is a capability, not a request to edit a name or evidence that adoption has completed.

Every updated response includes integer `naming_version`, reporting the authoritative adoption state of its returned binding: `0` for a historical binding, no current Key, or Miao; `1` for a Token Market Key issued under the new rule. The platform persists it atomically with the Key/configuration/binding transaction in `client_key_bindings.naming_version`. Display-name edits, profile changes, reconnects and client cache contents do not determine adoption. Historical bindings and proven historical credentials remain `0` until an explicit active migration issues an independent new Key.

Every newly issued Token Market Key adopts `1`, including requests from older clients. A personal Bound Workspace uses only the registered product display name. The canonical personal compatibility rule remains `defaultWorkspace == true || type == PERSONAL`. Enterprise names append the authenticated Key owner's primary full phone, then a bound PHONE contact (same feature preferred), then user ID. Only the `+86` component and its following separators are removed. Other international phone strings retain their country code. Names do not identify or merge device scopes. Miao retains `Miao-agent` and adoption `0`.

In the `llm-platform` repository, deploy `docs/sql/temp/20261105_client_key_naming_version.sql` before the updated services. It is idempotent and defaults every existing binding to `0`; the initial creation SQL contains the same column. No historical Key is renamed, reset, disabled or removed by this schema upgrade.

The shared CLI/desktop ConnectionManager sends capability `1` and encrypts the echoed version in its saved issuance receipt (absent legacy receipts deserialize as `0`). Safe credential storage still precedes confirmation, model loading and configuration commit. Active Connect/Reconnect inspects before any reuse. Capability `1` inspection of a legacy binding (including a deleted/missing current token), or an owned historical credential with no binding, returns `MIGRATION_REQUIRED` with adoption `0` after normal scope, status and expiry checks. Inspect does not issue, rotate, rename or mark that credential adopted. Legacy requests (absent/`0`) keep their existing inspection/adoption behavior and do not migrate a historical binding by reading it.

Capability `1` issue on a legacy scope creates an independent new identity with adoption `1` inside the existing scope transaction/row lock. It detaches all historical predecessor retirement links; none of those historical identities are reset or retired by migration completion or later recovery of the new Key. Repeated/concurrent issues see the same new `PENDING` binding; recovery rotates only that pending new identity. Existing request/generation guards reject delayed confirmations of the old identity. Capability `1` cannot recover, confirm or apply a legacy attempt instead of migrating; valid legacy attempts return `MIGRATION_REQUIRED` without mutation. Miao retains its separate legacy behavior.

Every updated response adds boolean `credential_matches` (Dubbo `credentialMatches`, default false). Only inspect sets it true, after checking that the supplied fingerprint matches the **returned identity's current active secret**. A stale historical ID/fingerprint must not conceal the current binding's disabled/expired state. A current new-rule pending binding is reported as `PENDING` even when the request supplies a stale historical ID or secret; `credential_matches` is false in that case, so the client recovers that same pending identity instead of pairing stale raw credentials with the new ID. Config-only credentials have no local ID and require the same fingerprint proof.

The updated shared manager reuses a credential only for adoption `1` plus authoritative `credential_matches: true`. Response version absence/unknown versions and legacy `VALID`/`PENDING`/`SAVED`/`APPLIED`/`LOCAL_COPY_REQUIRED`/`ISSUED` responses fail with a service-update error preserving existing credentials/configuration; explicit legacy `0` is accepted only for `MIGRATION_REQUIRED`, `NOT_FOUND`, `DISABLED` and `EXPIRED`. Ambiguous legacy `DELETED`/`SECRET_CHANGED` responses are rejected so an interim server cannot route replacement through a historical retirement chain. Encrypted receipts still deserialize absent historical adoption as `0`; response absence is distinguished from explicit `0`. No startup, login, list or background path initiates migration. Full mixed-version/fault coverage and independent review remain the downstream #43/#44 boundary.
