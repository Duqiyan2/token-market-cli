## Problem Statement

同一企业空间的多名用户接入同一个 Tool 时，平台创建的 Agent API Key 使用相同名称，
空间成员无法从名称识别工具和所属用户。现有名称中的 Token Market 前缀占用显示空间，
却没有提供用户区分信息。个人空间无需区分多个用户，Key 名称只需展示工具名字。

仅修改名称生成器不足以解决已有连接的问题：CLI 和桌面会复用本地凭据，平台也会按
现有连接范围找回旧 Key。清除本地缓存还可能触发凭据丢失恢复、重置旧 Key 的密钥，
或在恢复完成时停用旧 Key，不符合本次保留历史 Key 并重新创建的要求。

## Solution

新 Key 的 Key Display Name 按 Key 所属的 Bound Workspace 类型确定，均不带
Token Market 前缀：

- 个人空间：仅使用工具名字，例如 `Claude Code`，不附加手机号或用户 ID。
- 企业空间：使用“工具名字-用户标识”。用户标识优先使用所属用户的完整登录或
  绑定手机号，没有手机号时使用用户 ID。国内手机号去掉 `+86` 及对应分隔符，
  其他国际区号保留，例如 `Claude Code-13800138000`、
  `Claude Code-+44-7700900123`；无手机号且用户 ID 为 `12345` 时为
  `Claude Code-12345`。

个人空间即使有手机号也不追加用户标识；企业空间即使当前只有一个成员也沿用
企业空间规则。判定使用平台已有的空间类型及个人空间兼容语义，不依赖名称或成员人数。

历史 Key 不改名，也不因本次迁移而被重置、删除或停用。启用新规则后，用户下一次
主动 Connect 或 Reconnect 时，每个旧规则连接范围创建一个独立的新 Key；新凭据
安全保存、工具配置成功切换后，后续连接继续复用这个新 Key。同一用户在多台设备
使用同一个 Tool 时允许名称相同，底层 Key 的范围隔离保持不变。

## User Stories

1. 作为平台用户，我希望 Key 名称显示工具名字，以便识别该 Key 服务的 Tool。
2. 作为企业空间成员，我希望同一工具的 Key 名称包含所属用户的手机号，以便区分不同用户的 Key。
3. 作为平台用户，我希望名称直接使用所在空间对应的工具命名规则，以便无需阅读重复的 Token Market 前缀。
4. 作为在企业空间使用国内手机号的用户，我希望名称省略 `+86`，以便快速辨认熟悉的完整手机号。
5. 作为在企业空间使用其他国家手机号的用户，我希望名称保留国际区号，以便不同国家的号码不会混淆。
6. 作为使用手机号注册的企业空间成员，我希望平台使用我的完整手机号，以便管理员准确识别所属用户。
7. 作为注册后才绑定手机号的企业空间成员，我希望绑定手机号同样能用于命名，以便获得一致的识别效果。
8. 作为尚未绑定手机号的企业空间成员，我希望使用用户 ID 作为后备标识，以便无需补绑手机号也能接入工具。
9. 作为存在昵称的企业空间成员，我希望手机号或用户 ID 决定所属用户标识，以便同名昵称不会妨碍识别。
10. 作为使用多个 Tool 的用户，我希望所有受支持工具采用相同的空间类型命名规则，以便在空间中统一管理 Key。
11. 作为在多台设备使用同一 Tool 的用户，我希望允许 Key 同名，以便名称保持所在空间对应的命名格式。
12. 作为在多台设备使用同一 Tool 的用户，我希望各设备继续拥有独立 Key，以便名称相同不会合并连接范围。
13. 作为历史 Key 的持有者，我希望原名称保持不变，以便保留既有记录和识别习惯。
14. 作为历史 Key 的持有者，我希望迁移不重置、停用或删除原 Key，以便既有使用方继续工作。
15. 作为已有工具连接的用户，我希望下一次主动连接时自动采用新规则，以便无需手工删除本地凭据。
16. 作为尚未重新连接的用户，我希望当前工具配置继续工作，以便上线新规则不会立即打断现有使用。
17. 作为首次迁移的用户，我希望得到一个独立的新 Key，以便历史 Key 的身份和密钥保持原状。
18. 作为已经迁移的用户，我希望后续连接复用新 Key，以便反复操作不会产生重复记录。
19. 作为同时使用 CLI 和桌面的用户，我希望两者复用同一设备和范围的新 Key，以便两个入口不会各自迁移一次。
20. 作为拥有不同账号或空间的用户，我希望迁移范围继续隔离，以便其他连接不受影响。
21. 作为保留旧缓存或旧工具配置的用户，我希望系统正确识别旧规则凭据，以便旧副本不会绕过迁移。
22. 作为连接请求超时的用户，我希望重试继续同一次签发，以便网络异常不会创建多个新 Key。
23. 作为客户端中途退出的用户，我希望重启后继续未完成的迁移，以便已创建的新 Key 可以完成接入。
24. 作为本地凭据保存失败的用户，我希望现有工具配置得到保留，以便失败不会留下无法恢复的连接。
25. 作为模型目录加载或配置写入失败的用户，我希望下次重试复用已经安全保存的新 Key，以便失败不会导致重复签发。
26. 作为同时发起多个连接请求的用户，我希望同一范围最终只产生一个新规则 Key，以便并发操作不会制造重复记录。
27. 作为正常迁移的用户，我希望系统区分规则迁移和凭据丢失恢复，以便无需误报凭据丢失或停用历史 Key。
28. 作为已完成迁移后确实丢失凭据的用户，我希望继续使用现有显式恢复流程，以便后续凭据管理仍然可靠。
29. 作为更换手机号的用户，我希望普通重连继续复用已迁移的 Key，以便资料变更不会反复触发规则迁移。
30. 作为平台管理员，我希望用户归属、访问权限和连接状态校验继续生效，以便新命名与迁移流程不会绕过现有管理规则。
31. 作为个人空间用户，我希望 Key 只以工具名字命名，以便名称简洁且不包含手机号。
32. 作为没有绑定手机号的个人空间用户，我希望名称仍然只有工具名字，以便系统不会额外附加用户 ID。
33. 作为只有一个成员的企业空间管理员，我希望 Key 仍附加用户标识，以便未来增加成员时命名规则保持一致。
34. 作为同时使用个人空间和企业空间的用户，我希望 Key 根据各自 Bound Workspace 命名，以便切换 Current Workspace 不会改变已有 Key 的名称或归属。

## Implementation Decisions

- 修改平台客户端 Key 签发和绑定管理，以及 CLI/桌面共享的连接及凭据复用流程；仅改名称生成器无法满足迁移要求。
- 平台根据经过验证的 Bound Workspace 及既有个人空间判定语义决定命名分支，兼容已有个人空间记录。不得依据空间名称、成员人数、用户是否通过企业认证或客户端当前选择来猜测所属空间类型。
- 个人空间仅用工具产品展示名，不附加手机号或用户 ID；企业空间使用工具产品展示名与用户标识。
- 企业空间命名时，平台根据经过认证的 Key 所属用户读取手机号，优先使用主用户资料中的手机号，缺失时查找已绑定手机号，均不存在时使用稳定用户 ID。客户端昵称及客户端自行声明的手机号不能代替可信用户资料。
- 使用受支持 Tool 的产品展示名；保留既有工具标识、Key Source、归属和权限语义。名称不承担唯一约束，也不参与范围匹配或鉴权。
- 企业空间的手机号标识仅去掉国内手机号的 `+86` 国家码组件及其分隔符，保留号码本体；其他国际号码保留区号，不使用手机号脱敏结果命名。
- 同一账号、空间、设备和 Tool 的连接沿用既有客户端身份及服务地址隔离。CLI 与桌面共享范围，不因入口不同签发两个新 Key。
- 为绑定持久化明确的新规则采用状态或规则版本，现有绑定视为旧规则；不得通过可编辑名称、手机号或名称前缀判断是否已迁移。新安装首次签发也应直接记录为新规则。
- Client Key 协议需要明确区分旧规则替换、普通复用和凭据丢失恢复，使客户端能在保留旧缓存或从工具配置找回旧凭据时仍正确执行首次新建。具体字段和状态命名由实现确定。
- 旧规则首次替换创建独立 Key 记录并关联到当前范围，不重置历史 Key 的密钥，也不把历史 Key 放入会在接入完成时自动停用的恢复链路。
- 平台以事务和现有范围并发控制保证新 Key、绑定及迁移状态一致；重复请求、并发请求和响应丢失须收敛到同一次签发。迁移不应仅以配置成功与否决定是否再次创建 Key。
- 客户端沿用先加密保存凭据、再确认保存、加载 Model Catalogue、提交工具配置并确认接入完成的现有流程；中断后继续已持久化的签发状态，失败时保留现有可用配置。
- 完成迁移后恢复正常复用、校验和显式凭据丢失恢复；用户后来修改手机号或 Key Display Name 不触发重复迁移。新建 Key 时才使用当时的用户标识。
- 现有停用、过期、归属、权限、网络及存储错误处理继续生效；规则迁移不是绕过这些校验的途径。旧配置、凭据不得因服务不兼容或错误响应被误清除。
- 平台与 CLI/桌面需要配套实现和验证协议兼容行为。平台独立拥有命名和绑定状态，客户端不能单方面通过删除本地凭据完成本功能。

## Testing Decisions

- 测试边界已与用户确认：沿用现有 Client Key 协议和连接管理入口。客户端验证迁移、配置和复用，平台验证实际名称、历史 Key 保留及数据库并发一致性。
- 好的测试断言外部可观察结果：新 Key 的名称、ID 与可用凭据、旧 Key 是否未变、最终配置使用哪一个 Key、实际记录数量及重试后的结果；不通过私有辅助函数调用次数或某个版本字段名称替代行为验证。
- 客户端复用现有 ConnectionManager 协议测试方式：临时目录、本地 HTTP 平台夹具和测试凭据存储。现有先例包括签发响应丢失后重启、保存确认丢失、目录加载失败、缓存写入失败和显式凭据丢失确认。
- 平台复用 ClientKeyServiceTest 的服务入口及用户、空间资料依赖夹具，覆盖所有已注册 Token Market 工具、产品展示名及个人/企业两种命名分支。个人空间覆盖国内手机号、其他国际手机号、无手机号和已有个人空间兼容记录，全部断言名称仅含工具名。企业空间覆盖主手机号、后绑定手机号、无手机号、国内区号及其他国际区号；以实际签发结果或保存记录作为断言依据。
- 并发和事务保证沿用 ClientKeyAuditPostgresTest 的真实 PostgreSQL 测试环境，覆盖旧规则绑定迁移时两个并发请求只创建一个新规则 Key、旧 Key 保持原样，以及事务失败后不留下部分迁移状态。模拟 HTTP 或内存锁不能证明数据库锁与约束正确。
- 对旧 Key 留在缓存、连接记录、工具配置及平台绑定中的情况分别验证：下一次连接仍创建一个独立新 Key，完成后再次连接复用它，而不是重新认领旧 Key 或进入普通凭据丢失恢复。
- 验证已有旧规则绑定和无绑定但存在可认领旧 Key 的场景，防止旧凭据认领路径绕过迁移；无任何历史 Key 的新范围直接签发新规则 Key。
- 覆盖签发响应丢失、凭据保存失败、保存确认丢失、配置提交前后中断、模型目录加载失败及重启重试；断言恢复同一次迁移、历史 Key 未被重置或停用，配置不会引用尚未安全保存的凭据。
- 验证两个不同用户在同一企业空间接入同一 Tool 时名称可区分，只有一个成员的企业空间仍附加用户标识；同一用户不同设备可以同名但 ID 不同；同设备的 CLI 与桌面复用同一个新 Key。
- 验证同一用户在个人空间得到仅工具名的 Key、在企业空间得到带用户标识的 Key；命名跟随各 Key 的 Bound Workspace，而非稍后切换的 Current Workspace。两类空间均验证旧规则首次新建及之后复用。
- 验证账号、空间、设备、Tool 和服务地址隔离，及手机号或名称变更后不会额外迁移；已有停用、过期、权限、不可读凭据存储及服务错误的回归行为保持一致。
- 单次迁移的完整通过条件是：一个历史 Key 和一个新规则 Key 同时存在，历史 Key 的名称、密钥和状态未变，工具使用新 Key，后续重连没有新增 Key。
- 采用现有测试边界，不新建专用测试 API；真实平台与已安装客户端联调单独记录，自动化夹具通过不等同于生产部署或实机验收。

## Out of Scope

- 批量改名、清理、重置、停用或删除历史 Key。
- 每次连接都签发新 Key，或手机号、昵称、Key 名称变更自动触发再签发。
- 启动、登录或后台扫描时批量替换所有既有工具配置。
- 在名称里新增设备名、设备 ID、随机后缀，或要求名称全局唯一。
- 强制用户补绑手机号、企业空间改用昵称代替用户 ID 后备标识，或个人空间附加手机号/用户 ID。
- 改变现有 Key 权限、计费空间、登录授权方式和工具安装/升级行为。
- 将普通凭据丢失恢复改造成一律保留旧 Key；本规格仅为新规则的一次性替换保留历史 Key。
- 本次规格发布不包含业务代码实现、提交推送、生产迁移或部署。

## Further Notes

按个人/企业空间区分命名、手机号后备规则、区号格式、多设备同名及一次性新建后复用均来自本次对话中
用户的明确选择；测试边界也已确认。2026-11-05 按 to-spec 发布为可供 agent 实现的规格。

平台的名称生成与服务端绑定位于 llm-platform，客户端接入与复用位于 token-market-cli。
实施需要协调两端。只删除本地凭据、只改展示名，或直接调用会停用旧 Key 的现有
凭据丢失恢复流程，均不满足本规格。

既有共享凭据和配置保护决策继续适用；本规格增加旧规则 Key 的一次性替换例外，
其余连接生命周期遵循原有语义。规则版本和协议状态的具体设计属于实现细节，
应以本文的可观察验收结果评审。
